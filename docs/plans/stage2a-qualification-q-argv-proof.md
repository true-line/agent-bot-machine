# Stage 2a Q cross-UID argv proof

## Intent

An A-started, dedicated qualification process Q must be tied to the exact owner-reviewed launchd command before its observations enter a one-use Stage 2a run. The proof is an admission input. It is not a test verdict or physical T03 evidence.

## Target

- The A-local observer loads the installed Q review and live reservation, checks the paired run, and creates one A-owned listener for that start. The root-reviewed Q install pins HQ's UID and GID separately against the installed HQ account; the reservation's HQ UID joins to that UID, never to the HQ GID. Production uses the cross-UID argv proof for every installed Q start.
- A reads the retained qualification plan from the root-owned Q installation directory. It recomputes the canonical plan digest pinned by the installed review and checks the physical host, test plan, provider configuration, and native harness before Q starts. The run must name the same suite revision and runner account and UID as that plan.
- Before creating the listener, A checks its exact stored reservation and active-start claim under the per-installation lock and durably spends a Q session name for that start. A failed spawn or handshake leaves it spent; daemon restart cannot replay it. A new start needs a new reservation and Q session claim.
- A can publish the Q wire, signed frame index and signed EOF receipt only while the exact durable Q session claim and stored reservation both exist under the same installation lock. A fabricated completed session without that spent claim cannot publish pre-sign evidence; closing the start does not erase an already spent Q claim.
- After authenticating Q's Ready, A durably binds the spent claim to that exact session ID, Q challenge, kernel PID/UID/GID/start, socket identity, executable and argv. The binding is published at most once while the start is active; pre-sign publication requires its exact bytes even after the start has closed. A different Q session cannot inherit the spent claim.
- Immediately before launch, A reloads the installed Q record, compares the launchd plist with its rendered bytes, requires the job to be loaded, and verifies the installed launcher, Node, and PS signatures. The launcher accepts only its fixed Q command. No extra account, socket, network allowance, or root-run Q path is introduced.
- Q writes its PID on the launchd trigger stream and closes its write half before waiting on the separate session socket. A requires EOF on that trigger before accepting the PID, even when launchd retains a socket reference.
- After launchd starts Q, A binds the accepted Unix peer to the kernel PID, real/effective/saved UID, real/primary/saved GID, parent PID, process start, and Node image. It observes the image between two matching kernel snapshots to reject PID reuse. It checks the Q group set and rechecks that identity around every protocol frame.
- A sends a fresh one-use challenge only after authenticating the peer. The pinned Q code reports its exact executable and argv in Ready with the challenge digest; A compares those fields to the installed command. A validates the same fields again when joining the final canonical transcript. Missing, changed, or extra fields fail closed.
- The proof stays inside the existing A/Q qualification exchange and signed reservation. A continues to hold keys and protected operations in its secure administrator account.
- For direct T21, A admits only the current attached cooperative reservation with the retained schema-2 Q plan and measured direct-Comms R/H. It spends the direct Q claim before leaving the short paired admission lock, then runs the fixed T21 pre observation while ordinary HQ liveness refresh remains available. The signed pre response binds Q's session, challenge, plan, pre observation, one-use case nonce, and short deadline to the exact reservation and attach.
- HQ performs its protected-profile claim attempt between A's pre and post phases. A accepts only the exact canonical durable `profile_insufficient` HQ receipt through a new signed paired finish request, bound to the pre response, Q challenge, case nonce, reservation, attach, and cooperative start receipt. A rechecks live R/H kernel and claims, captures Q's post observation and clean EOF, persists the Q wire and signed index/EOF, and signs an explicitly unqualified capture with no host credit. Failure or restart leaves the Q claim spent; stopping the cooperative start closes an active Q session.
- A proposed owner-driver control listener uses a separate socket in A's existing mode-0700 `<A home>/.config/agent-machine` state directory. A derives the basename as `qd-` plus the first 16 bytes (32 lowercase hex characters) of SHA-256 over `agent-bot-machine/stage2a-qualification-driver-installation/v1` followed by a zero byte and the installed Q review's installation ID, plus `.sock`. The owner-reviewed test plan pins that exact path before Q plan creation. A no-follow checks its ancestry and exact owner/mode, refuses a preexisting socket, binds a one-use socket, and sets mode 0600 through the anchored parent descriptor without following a substituted symlink. A proves that the recorded pathname reaches its listener with a same-process challenge. It rechecks parent and socket inode/birth identity and authenticates the kernel peer UID/PID/start and exact reviewed executable/argv before consuming any control message. Closing the listener leaves its pathname occupied: Darwin cannot condition an unlink on the observed inode. A distinct installation has its own one-use pathname, so the sibling baseline Q can close before the primary live-T03 Q binds without retiring the sibling socket. Reusing the same installation pathname requires explicit reviewed recovery. The listener does not implement a driver protocol or admit a physical report by itself. The final signed driver and owner plan must pin the exact home, path, code, argv, case protocol, and recovery ceremony before activation; no root-run driver or new shared socket is permitted.

- The owner-driver case exchange pins the socket, native executable hash and exact argv from the reservation's reviewed test plan. A selects a fixed schedule for the local profile and launch phase. Each case carries a fresh challenge and joins the reservation, start, session and exact request bytes. A resolves the returned digest to authenticated fixture evidence and independently derives the OS observations for Q.
- A can sign a separate driver capture receipt over the admitted process generation, exact paired case frames, A's OS witness digests and the joined Q transcript. A opens Q after the durable reservation and may keep the session open across launch publication. The before-launch cases establish a baseline. Live and restart cases need their corresponding host state, and restart uses a new reservation and Q session. A later phase for a different installation uses its own reviewed pathname; reusing the same installation requires explicit retirement of that installation's one-use pathname. Q removal after the sibling baseline leaves the sibling socket occupied and does not retire its active Soul start.
- The installed Machine binary's `stage2a-qualification-owner-driver` worker runs without arguments in A's nonroot account. The test plan pins the worker and daemon argument vectors and the private listener path. The before-launch driver checks the installed local provider configuration and, for protected starts, the reviewed enforcement policy file. A and the driver each hash the pinned file and sample its OS metadata. A protected reservation with the matching root-installed `driver_baseline_only` review must durably capture this baseline after the reservation and before bridge publication. The archive commits the raw source and OS witness bytes and their A signature joined to the exact Q wire, index and EOF receipt.
- An owner-reviewed `driver_live_t03` installation keeps the exact A driver and Q session open across one protected start. A verifies the T02 custody and T03 policy baselines before publishing the bridge proof. After A authenticates the first response over the HQ-hosted provider route, A rechecks the protected child receipt and live role identities. The driver acknowledges the live T03 challenge before A arms the R stimulus. A sends the corroborated artifact digest to the driver and asks Q for independently selected OS observations. The signed archive joins the baseline, live artifact, OS witnesses, Q transcript, index and EOF receipt. This phase covers live T03 evidence. The T01 and live T02 cases retain their separate evidence requirements. The baseline-only and live flags select which cases the one-use worker runs.
- The direct-denial stimulus also needs a second, concurrently active R installation with a distinct runner UID, finalized B bind, child receipt, and reviewed sibling credential and socket paths. A checks that sibling before arming the first R and again before accepting its completed probe. Both installations and the exact installed CLI must appear in the new owner-reviewed physical plan; a fixture or a prior signed artifact cannot supply this evidence.
- Before B writes the protected T03 positive response, it reports the prepared HTTP wire digest and length, exact nine-integer Darwin audit-token peer record, and canonical peer digest on its already bound broker connection. HQ forwards the strict prewrite record through the paired Machine channel while B holds that accepted R-to-B Unix connection. A joins the peer parent PID, UID and start to its observed ACP child, freshly observes the live stock CLI PID, start, UID and installed executable, and returns a signed one-use receipt. B waits for that receipt and rechecks the same kernel peer immediately before the full response write.
- Only after a successful full write does B report the actual wire digest, length, status and write times with the same peer and prewrite receipt. B authenticates the exact canonical completion with a completion-only subkey derived from its existing A:B proof before the bind step clears the raw FD4 key. The subkey is cleared after the one completion or on exit; HQ never receives either key or a MAC oracle. A verifies the MAC against its retained proof, current reservation and one-use prewrite, joins the actual write to the prepared intent and HQ's positive receipt, and commits its earlier live CLI witness with the completion. A permits the one-shot CLI to exit after the write; a missing, partial, stale or mismatched B completion fails closed. The signed live Q archive carries the resulting A-owned peer witness and authenticated B completion. This source gate does not by itself establish physical T03.
- The sibling R child observes the reviewed credential file from inside its own 0700 home. It opens each path component without following symlinks, requires sibling ownership, 0700 ancestor directories, a nonempty single-link regular file with 0400 or 0600 mode and no allow ACL, and reads no credential contents. Its metadata record uses schema `agent-bot-machine/stage2a-t03-credential-metadata/v1` and the fields `path`, `device`, `inode`, `generation`, `uid`, `gid`, `mode`, `size_bytes`, `birth_seconds`, `birth_nanos`, `modify_seconds`, `modify_nanos`, `change_seconds`, and `change_nanos`. Device, inode, generation, size and time values are canonical decimal strings; UID and GID are integers; mode is a four-digit octal string. The reviewed `sibling_credential_metadata_sha256` is the `sha256:` digest of that record's JCS bytes. No A, H, B or Q process gains traversal of the sibling home or reads the credential.
- A sends a short, challenge-bound credential probe only in a signed Live lease to that sibling child. The R-UID child wrapper first sends the observed metadata directly to A's existing cross-account Machine socket. A accepts only the exact active wrapper's Darwin kernel UID/PID/start and current HQ epoch, rechecks the stock child, and stores the bounded record. This direct route only ingests data and returns an unsigned `ok` bit; it cannot request a protected operation or obtain an A signature. HQ then forwards the exact child status event to the paired Machine witness verb, which accepts only an identical, fresh direct child record. A checks the current child receipt, lease sequence, challenge, path and reviewed metadata digest before its paired ACK. One acknowledged witness is required before primary T03 arm; a second from a later lease issued and observed after the primary credential open attempt is required before completion. The Q OS witness commits both accepted records and their A-observed peer identity. Missing, stale, substituted or same-lease records fail closed.

## Acceptance

- An installed, owner-reviewed Q plan starts with exact kernel identity, loaded command, signed images, challenge-bound Ready argv, and a clean one-use exchange.
- Wrong UID/GID, parent, image, start, group, installed plist, argv, challenge, or resumed PID is refused. A Q fixture cannot make the protected positive-start gate true or establish T03.
- A missing active-start claim, substituted reservation bytes, or second Q session for one start is refused before Q is launched.
- A Q Ready for another session ID, Q challenge, socket or kernel identity cannot reuse an existing session binding for pre-sign evidence.
- A missing trigger EOF is refused within the bounded launch window; a disposable guest must also demonstrate that the reviewed Q completes the trigger handshake before Ready is assessed.
- The same run must be repeated on the exact owner-approved physical host with both dedicated R accounts, released H/R/Souls/Contracts pins, protected cutoff, and safe retirement before any physical T credit is claimed.
- T03 receives no credential-denial credit for a nonexistent or mismatched sibling file, a symlink or changed owner/mode, a different reviewed metadata digest, a missing later-lease sibling witness, or a forged HQ-only forward without the exact kernel-authenticated child-origin record. A mixed CLI output that names the target on one line and reports an unrelated denied `connect` on another is not a direct-denial record.
- A driver transport with the wrong state directory, installation-derived pathname, UID/GID, socket inode, peer PID/start, executable, or argv is refused. A substituted symlink cannot cause mode changes outside A's state directory. The sibling and primary installations can bind distinct reviewed one-use sockets in sequence while the sibling remains active. A leftover socket for the same installation is never silently adopted or unlinked before a reviewed recovery decision.
- Direct T21 begin/finish reject stale R/H kernel identities, stopped or restarted starts, a second Q claim, altered pre selectors, late or noncanonical HQ refusal receipts, and any request for a protected start from this cooperative route. A capture remains unqualified until separate physical-host review and the full T21 verifier exist.

## Replay

Run `go test -p 1 ./internal/members ./internal/daemon` and `go vet ./...` from the repository root. For the disposable macOS Q component, record the exact source tree and signed binary digests, installed Q review/plist, kernel observations, Ready argv/challenge digest, cleanup, and the guest deletion receipt. Compare the released packet and physical host plan independently before a positive qualification run. Record both installation IDs and their exact derived driver socket paths in the owner-reviewed test plans; after the sibling baseline, remove the idle sibling Q installation while preserving its active start and occupied socket, then install the primary live-T03 Q. Replaying either installation's occupied pathname must refuse. A fresh Machine binary changes the launcher digest, so regenerate pending R/H/Q plans and the signed guest artifact for the exact head; existing applied R/B account receipts remain valid.
